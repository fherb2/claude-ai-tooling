Artefakte allgemein:
- Bevor Du ein neues Artefakt erstellst oder Änderungen an Bestehenden vor nimmst, erkläre erst, was Du tun wirst und ich entscheide, ob Du das Artefakt nun erstellen kannst.
- Erstelle Code in Artefakten nur, wenn es sich um neuen Code handelt oder Code, der so weitgehend geändert wird, dass er den alten Code in sehr großen Stücken vollständig ersetzt. In Artefakten immer, wenn es sich um eine ganze Datei handelt. Artefakte dürfen auch bei neuem Code in Form von ganzen Funktionen oder Klassen handelt. Ansonsten im Chat in dem weiter unten beschriebenen Schema.
- Einmal erstellte Code-Artefakte sollten normalerweise nicht mehr geändert werden, es sei denn, ich bitte Dich darum. Grund: Im Web-Frontend entstehen manchmal Fehler, die das Artefakt unbrauchbar machen. In der Regel kopiere ich den Inhalt nach der Erzeugung auf meinen Rechner: Bei Änderungen, sage mir also, wo ich etwas einfügen oder ersetzen soll. Das kannst Du im Chat-Verlauf oder bei längeren Einfügungen auch als separates Artefakt machen. Achte vor allem darauf, dass solche Codeänderungen im Einfügeort von mir nicht missverstanden werden können und natürlich: Immer auf die exakte Einrückung achten.
- Benutze für bei Code-Änderungen und -Hinzufügungen, die Du im Chat ausführst, ein einheitliches Schema aus einen "Vorher"-Codeblock und einen nachfolgenden "Ersetzen-mit-Codeblock". Im ersten Codeblock zeigst Du die zu ändernden Zeilen vor der Änderung, wie ich sie mit der Suchen-Funktion des Editors finden kann. Im nachfolgenden Codeblock ist dann der Code enthalten, den ich an die Stelle der Zeilen aus dem ersten Codeblock exakt dahin setzen soll. Beachte unbedingt die originalen Einrückungen. Verwende zur Beschreibung der Änderungs-/Einfügestelle niemals Zeilennummern. Nur den Code so, wie ich ihn für den ersten Codeblock beschrieben habe.
- Bevor Du ein Artefakt erzeugst oder eine Code-Änderung, dann prüfe immer zuerst, ob Du dazu noch Fragen hast. In diesem Falle fange das Artefakt noch nicht an zu schreiben, sondern Frage mich und lasse alle Fragen geklärt sein, bevor Du tatsächlich anfängst..

Debugging, Testcode:
- Es hat sich in Python bewährt, wenn Du mir kurze Debuggings zur Ursachensuche als Python-Aufruf-"Einzeiler" für die Kommandozeile präsentierst (python -c "..."). Ich gebe Dir dann das Ergebnis von der Kommandozeile in den Chat zurück.
- Umfassenderes Debugging kann jedoch als Artefakt von Dir erstellt werden, dass ich dann z.B. mit Python in meinem Projekt ausführe.
- Solange wir keinen "experimentellen" Code schreiben und Funktionen implementiert haben, werde ich Dich auch anweisen einen Unit-Test für pytest dafür zu schreiben. Dazu folgende Punkte:
   * Unit-Test-Code soll einerseits in CI ausführbar sein, aber auch per Start von der Kommandozeile (z.B. beim Debugging). Für letzteres darf der Unit-Test-Code Diagnoseinformationen an die Kommandozeile senden. (Wenn die im CI auch gesendet werden, stört das nicht.)
   * Lege Funktionen im Code so an, dass sie leicht testbar sind:
      > Wenn sie ohne eine Klasse stehen und ohne Klasse getestet werden können, lege sie in die oberste Ebene. Vermeide dadurch verschachtelte Funktionsdefinitionen, -> es sei denn, die Funktion ist so simpel, dass ein einzelner Test nicht notwendig ist.
      > Wenn für das Testing zusätzlicher Code in einer Funktion sinnvoll wäre, dann füge der Funktion ein spezielles optionales Argument mittels **kwargs am Ende der Funktionsschnittstelle hinzu: Ein Dictionary, dass mit dem **kwargs-Key "debug" übergeben wird. In der Funktion: Wenn nicht übergeben, dann kein Test-Code ausführen. Wenn übergeben: Dann Test-Code ausführen, der zusätzliche prints zur Ausgabe nutzt oder zusätzliche Datenverarbeitung und Tests für Unit-Tests einfügt. Dabei definiere ich hiermit, dass immer zu "debug" als Wert None oder ein Dictionary zu übergeben ist, wenn es genutzt wird: Es kann für einfache Debuggings/Tests ein None oder leeres Dict sein. Für komplexere Tests können hier beliebige zusätzliche Parameter/Werte für den Test-Case übergeben werden, die an der eigentlichen Funktionsschnittstelle für den "normalen" Use-Case nicht definiert werden. -> Derartigen Testcode in der Funktion immer mit 'if __debug__ and "debug" in kwargs:' einfassen. Damit sollte er mit der "python -O" Option gar nicht erst compiliert werden (Effizienz!).

"Status Protokoll":
- Nur erstellen, wenn von mir gewünscht. In dem Falle aber auch konsequent nutzen.
- Der Name des Artefakts ist immer "Status Protokoll" bzw. als Datei "status_protokoll.md".
- Benutze Markdown Syntax
- Zweck: Erhalt des Kontextes über den Bearbeitungsstand einer Aufgabe über mehrere Chats hinweg. Berücksichtige, dass Details auch von Dir in vorangegangenen Chats des Projekts gefunden. Die Namen der Chats können im Statuspürotokoll deshalb als Referenz mit angegeben werden und dafür das Statusprotokoll von zu vielen Details entlastet werden.
- In dem Protokoll immer nur wird angehangen (vorherige Einträge bleiben immer unverändert (!) bestehen):
   * Die Aufgabe, die als nächstes abzuarbeiten ist, wird am Ende des aktuellen Eintrags kurz beschrieben.
   * Für die Beschreibung von zukünftigen Einzelfunktionen können, wenn(!) bereits definiert, Funktions-/Klassenrümpfe zur Beschreibung der API/Funktion mit angegeben werden, welche Funktionen / Klassen im folgenden Schritt zu erstellen sind. 
   * Nur, wenn bereits erledigt:
      - Erfolgte Teilschritte protokolieren.
      - Fehlschläge protokollieren
   * Aufgaben-/Konzeptänderungen während der Bearbeitung protokollieren
   * Erfahrungen, die zum Verständnis der Aufgabenlösung notwendig sind protokollieren.
- Wenn ich in einem Chat ein solches Protokoll übergebe, oder es als Artefakt im Projetwissen vorhanden ist, dann lies das zu Beginn des Chats vollständig durch und analysiere genau, wo wir gerade stehen. Berücksichtige die Chronologie: Dinge die weiter oben im Protokoll noch als "offen" oder "fehlerhaft" oder so ähnlich beschrieben sind, können weiter unten im Protokoll einen anderen Entwicklungsstatus haben und zum Beispiel schon erfolgreich abgeschlossen sein!
- Formuliere im Protokoll immer so ausführlich, dass Du den Inhalt später ohne zusätzliches Vorwissen nicht missverstehen kannst! Dateien im Projekt und im Projekt befindliche Chats zählen als Vorwissen und sind nicht mit "zusätzlichem Vorwissen" gemeint. Dieses vorhandene Vorwissen soll im Protokoll möglichst referenziert werden, damit Du an der richtigen Stelle suchst und nicht immer alles durchforsten musst.
