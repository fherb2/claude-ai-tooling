# git-branch-model — running a Git project with a development, a release and a management branch

*Last updated: 2026-09-16*

*[Deutsche Fassung](https://github.com/fherb2/claude-ai-tooling/blob/master/skills/git-branch-model/README.md)*

**✅☑ Finished and usable.** Instructions complete, frontmatter set, silent trigger present; German and English versions available. — Usable with Claude Code.

**Gives a Git project four branch roles and the rules for how work moves between them — and thereby solves the problem that files like the project CLAUDE.md, the editor configuration or the `.gitignore` must be identical on every branch, yet no merge brings them there reliably.** A development branch carries everything in progress; topic branches branch off it and return by merge; a release branch carries the published state and is not a place to work. The fourth role is the actual invention: a **management branch** with no common ancestry with the others, carrying exclusively the central files and never merged — its files are laid over every other branch via `git restore --source`. A sync checks the direction while doing so: the outdated is overwritten, the new is reported. For the release transfer the skill knows two modes, because a project with several products cannot merge but transfers file by file.

**Scope:** The skill applies only to Claude Code working locally on a Git repository, not to claude.ai. It governs the branches of a project, not how a single session commits — whether on a workbench with intermediate states, in its own worktree, or directly; that is a separate capability, and this skill does not presuppose it. It only demands that a machine's intermediate states do not reach the development branch in machine granularity.

## Installation

1. **Download the package.** `downloads/git-branch-model_en_local.zip`

2. **Unpack.** The archive contains a folder `git-branch-model/` with all files. Unpack it into `~/.claude/skills/` — then the skill applies to all projects — or into `.claude/skills/` in the project, then only there. An existing folder of the same name is replaced; nothing old is left behind.

3. **Adopt the silent trigger.** You have to do this by hand. Claude then recognizes more easily from the context whether the skill should be loaded. To do so: from `CLAUDE-snippet.md`, **everything below the separator line** goes into the `CLAUDE.md` of the chosen location. The italic text above it stays behind; the file itself remains in the skill folder and shows, by its date line, which state the adopted trigger is from.

   Without this step the skill only works when called explicitly with `/git-branch-model`.

4. **Wire the hook.** This too you have to do by hand, and it comes in addition to the trigger, not in its place: the trigger covers the occasions (release, branch, central file); the hook covers the one case in which the trigger does not fire with some models — the first writing Git command in a project with `.claude/git-branch-model.json` (measured with Sonnet, see "Status and open points"). It refuses that first command once, until the skill is loaded; afterwards it stays silent for the rest of the session. Everything about it is in `settings-json-snippet.md`: the finished entry below the separator line, above it where it belongs, how it is inserted into an existing `settings.json` and — if you did not unpack into `~/.claude/skills/` — how to adapt the path. There is also a check that verifies the entry immediately, without waiting for a Git command; run it, because a wrong path shows up nowhere else. The file remains in the skill folder afterwards; its date line shows which state the adopted entry is from.

   Without this step the skill works via trigger and call; the guaranteed notice before the first writing Git command is then missing. In this repository the `settings.json` lives on the management branch `repo-management` — that is where it is changed.

5. **Set up per project.** The branching model does not take effect through the installation but through the initial setup in the project: branch names, kind of release transfer, list of management files, the file `.claude/git-branch-model.json`. It happens in the chat, at the user's request; the skill guides through the steps and explains along the way what happens automatically from then on and what is asked. Without it the skill does nothing — except offer the setup when an occasion arises.

The `README.md` comes with the package, and for good reason: the `SKILL.md` refers to it for all reasoning, and Claude names it as the reference when the skill first takes effect and quotes from it when asked. Whoever just installs the skill and watches what happens thus gets the explanation when they need it. If the README is missing, the skill still works — answers to why-questions just come out thinner.

## Details

**Two parts: thin `SKILL.md`, loaded rules file.** The skill deliberately fires broadly — also in projects that keep no branching model. So that those sessions do not carry the full rules text in context, the `SKILL.md` only establishes the situation and loads the rules file (`rules.en.md` or `rules.de.md`) only once the model holds or is to be set up.

**Why an orphan management branch with `restore` instead of a merge flow.** Two reasons, and each alone would carry. First the squashes: where a session's intermediate states arrive on the development branch as one commit, ancestry is lost — if a central change were distributed by merge and squashed afterwards, the development branch would know nothing of the common origin, and the next merge of the same state would produce conflicts in files where there never was a real conflict. Second the partial transfer: whoever publishes only part of the development state cannot merge the release branch, and then the central files reach it on no merge path at all. `git restore --source=<management>` bypasses ancestry completely: there is exactly one valid version of every management file, and overwriting is always the right resolution. That is exactly why the rule "no durable change to management files outside the management branch" is not tidiness but the condition under which the procedure is conflict-free.

**Why the sync checks the direction.** "Overwriting is always right" holds only as long as the local version is *outdated*. If someone accidentally changed a management file on the development branch, the local version is *new* — and a sync that overwrites blindly destroys that work. Exactly that happened in the first project using this model: a drift between development and management branch in which the prescribed sync became a reset trap. The direction is mechanically determinable: the content of the local file (`git hash-object`) either occurs in the management branch's history (`git log --find-object`) — then it is outdated — or it does not — then it is new. Only the first case is fixed automatically; the second is reported, with the proposal to bring the change onto the management branch. That is why the sync no longer runs "at session start, automatically" but "before the first writing Git command, depending on direction": session start is a state an instance cannot detect reliably; the first writing command is an action that occurs in every relevant session.

**Why distribution is pull-based.** The management branch pushes nothing into the other branches; every session fetches the state itself. That turns temporary deviation into an intended state instead of an error: an experiment — a central change one session is to try out before it holds for everyone, say a new paragraph in the CLAUDE.md or a hook in the settings — is simply a sync not yet run plus a marked local change. It is ended by the same sync, one command, no editing back. The marks (`MANAGEMENT-EXPERIMENT`) are not decoration: before every release transfer, forgotten experiments are found through them — mechanically, not by memory.

**Why two kinds of release transfer.** A project with one product merges its development branch into the release branch, and the history stays continuous — the normal case everyone knows. A project with several products, however, often wants to publish only one of them, and there is no merge for that: it takes all or nothing, and after the first partial transfer every later merge reckons with a merge base that never described the actual state — the same phantom-conflict mechanism as with the management branch. The `file-sync` mode draws the consequence: separate histories, transfer file by file, the release branch is never checked out. "Every commit is kept" then holds within the development branch, not across the boundary. The skill names the invariants of this mode; the concrete transfer recipe — which files are meant to be absent, what the cross-check looks like — belongs to the project that needs it. In the first project using this model that is a tool of its own under `.claude/skills/`, living only on the development branch.

**What belongs on the management branch — and what does not.** The criterion is "must be identical on every branch", not "is configuration". That is why tooling with logic of its own belongs there when it is branch-independent — a project skill, a CI configuration —, and why a tool needed only on the development branch does *not*: distribution would put it onto the release branch too, where it would be out of place. The model's own configuration file is in the list; it must be the same everywhere, otherwise two branches read two different models.

**Why changes to the management branch happen in a temporary worktree.** The branch is orphan and carries only a few files. Checking it out in the main checkout would mean emptying the working tree down to those files — every open piece of work would have to be stashed first. A temporary worktree (`git worktree add <tmp> <management>`) leaves the main checkout untouched and disappears again after the commit.

**Why tooling on the management branch may be developed on a working branch.** A skill or a hook is developed iteratively, with intermediate states. On the management branch every commit requires approval — unusable for iterative work. The solution is a working branch that branches off *the management branch* and returns into it by squash. That does not violate the invariant "derived from no other branch, never merged": it means the traffic with development and release branch. A branch coming from the management branch contains only management files, and the squash keeps that branch's history clean.

**Hardening option, not part of the skill: a `pre-commit` hook.** The sync catches what a Claude session does. If the user themselves changes a management file on the wrong branch, only a session's next sync notices. Whoever wants to catch that mechanically can use a `pre-commit` hook that checks before every commit whether management files differ from the management branch and otherwise refuses the commit — for human and machine alike. The price: hooks live in `.git/hooks/` and are not versioned. Via `core.hooksPath` a versioned folder (say `.githooks/`, itself on the management branch) can be set as the hook location, but that setting lives in `.git/config` and must be set once on every machine — forget it, and the protection is silently absent. Besides, `--no-verify` bypasses every hook, and a marked experiment would have to be let through. That is why this is a decision of the project, not a rule of this skill.

**Known limitation: collision with the Bash sandbox.** If Claude Code's sandbox is active, creating a worktree — which the skill needs for changes to the management branch — can fail on a known collision after which every Git command fails ([issue #80278](https://github.com/anthropics/claude-code/issues/80278)). The rules file carries a short marked note for this (`TEMP ISSUE-80278`): if the sandbox is running, the user is asked before the first `git worktree` command whether it can be switched off briefly. Once the issue is closed, the marked note is removed.

**The skill's approval tiers** (table in the rules file) settle conclusively what happens automatically, what after asking, what once per project and what every time — explicitly also where something else has been agreed elsewhere for comparable activities. Automatic is only the sync in the "outdated" direction and reading; everything that creates, deletes or merges a branch or changes the management branch remains subject to consent.

**Rules whose simplification destroys the function:**

- The management branch is never merged and never derived from another branch. Whoever branches it off `master` "for simplicity" invites merging it — and thereby tips an outdated overall state over the target branch.
- The sync overwrites only the outdated. A sync that "saves" the direction check is the reset trap it was built against.
- Experiments on management files end through the sync, never through merge and never through manual rollback.
- In the `file-sync` mode the release branch is never merged. A "quick merge" after a partial transfer produces conflicts that are none.

**Technical prerequisite:** Git ≥ 2.42 for the initial setup (`git worktree add --orphan`), Git ≥ 2.16 for the direction check (`git log --find-object`). Everyday use otherwise gets by with older versions.

**Extending.** The project-specific names belong in the project's `.claude/git-branch-model.json` (fields: `integration_branch`, `release_branch`, `release_transfer` with the values `merge` or `file-sync`, `management_branch`, `management_files`), not in the skill text — otherwise one project's scheme suddenly applies to all projects. The `git-` prefix in the file name lowers the risk of a collision with future engine files in `.claude/`.

## Status and open points

**Status:** New since 15 September 2026, extracted from the former skill `parallel-sessions`, which mixed branching model and workbench; this repository is at the same time the first project using the model. Decided are: the four roles; the two modes of release transfer; the sync with direction check instead of the blind sync at session start; that tooling with logic of its own may go onto the management branch when it is branch-independent; that working branches off the management branch are permissible.

**Measured (16 September 2026, procedure per chapter 4.2 of the guidelines, 34 runs with Sonnet, Opus and Fable):** On a plain commit request that names neither release nor branch, the trigger fires with Opus and Fable but **not with Sonnet** — there, at the anchor "first writing Git command", only the skill whose description literally matches the request is loaded, and the check "does `.claude/git-branch-model.json` exist?" from the CLAUDE.md trigger is not carried out. As soon as `master` or a release is mentioned, it fires with all three. A description that names the commit case together with the file condition itself changes nothing (0 of 3 with Sonnet); it was discarded. All statements here rest on runs **with** the configuration file present — the runs meant to measure without it ran with it as well, due to a defect in the test setup (a `reset --hard` restored the removed file from the test project's history); the case without the file is not measured for this skill. **Consequence for Sonnet users without the hook:** the sync of the management files then does not run at every first commit but only once an occasion with release or branch reference arrives.

**The answer to that: the hook (`notify_branch_model.py`, installation step 4), built and measured on 16 September 2026.** A `PreToolUse` hook on writing Git commands denies, in a project with `.claude/git-branch-model.json`, the **first** such command of the session with the reason to consult the skill first — and only the first: whether the skill has already been loaded it reads from the session transcript Claude Code hands to every hook. The sync of the management files thus runs before the first write, not after it. Two variants were measured (Sonnet, three runs each, default permission mode, in a throwaway project with load indicators): a mere notice via `additionalContext` did make the instance load the skill (two of three; the third run failed on a gap in the command list, closed since), but only **after** the command — `additionalContext` stops nothing. The once-per-session block instead: **three of three** runs with the file were refused, the instance loaded the skill and repeated the command; without the file the hook stayed silent in three of three runs. Built according to chapter 5.0 of the guidelines, with two findings from the hooks reference: command-level filtering via the `if` field (matchers filter by tool name only), and the refusal with its reason reaches the instance as a tool result — plain stdout text does not reach it with `PreToolUse`. If the hook cannot read the transcript, it does not block but only gives notice.

**Deliberately left open.** The concrete branch names, the kind of release transfer and the list of management files are decisions of the respective project and live in its `.claude/git-branch-model.json` — the skill carries only the procedure and the roles. Likewise the transfer recipe for `file-sync` and the decision whether a project puts its tooling onto the management branch.
